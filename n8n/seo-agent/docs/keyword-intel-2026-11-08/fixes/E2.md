## 1. The workflow (150 nodes, `workflows/SEO_Agent_Keyword_Intelligence.json`)

```
Manual Run -> KI Input -> Ensure KI Runs / Competitors / Keywords / Gaps Table -> Load Monitors (KI) -> Load Kill Switch (KI) -> Load Site (KI)
  -> KI Gate -> KI Refused? --yes--> Has Callback (KI Refusal)? -> POST KI Refusal            (no ledger row, nothing paid, nothing written)
                            --no---> Load KI Cache / KI Competitors / KI Gaps / Query History / Ladders / AI Visibility / AI Answers / Pages
  -> KI Plan -> [ledger_mainline] Ensure Run Ledger -> DFS Balance -> Load Open Runs -> Run Ledger Row -> Reserve Run Ledger -> After Run Ledger
  -> Run Allowed? (KI) --no--> Refuse Run Ledger -> Refusal Notice -> Post Refusal          (the run guard: twin per kind and site, open runs)
                       --yes-> Load Ledger Today (KI) -> KI Limit -> KI Limited? --yes--> Refuse KI Limit (KI) -> KI Limit Notice -> POST KI Refusal
                                                                                 --no---> KI Started -> POST KI Started -> Route KI Kind?
Competitors:  Comp SERP Keys -> Load SERP Cache (KI Comp) -> Comp SERP Requests -> [Run Comp SERPs + gate] -> Comp SERP Picture
  -> Comp Labs Requests -> [Run Comp Labs + gate] -> Comp Candidates -> Comp Home Requests -> Read Comp Homes (free GET)
  -> Comp Profile Requests -> [Run Comp Profiles + gate] -> Comp Sitemap Requests -> Read Comp Sitemaps (free GET) -> Comp Result
  -> KI Comp Rows -> Save KI Competitors (upsert site_id + market + comp_domain) -> KI Comp Drops -> Drop KI Competitors
Research:     Research Seed Keys -> Load SERP Cache (KI Seeds) -> Research Discover Requests -> [Run Research Discover + gate] -> Research Candidates
  -> Research Enrich Requests -> [Run Research Enrich + gate] -> Research Picture -> Research SERP Keys -> Load SERP Cache (KI Research)
  -> Research SERP Requests -> [Run Research SERPs + gate] -> Research SERP Picture -> Research Traffic Requests -> [Run Research Traffic + gate]
  -> Research Result -> KI KW Rows -> Save KI Keywords (upsert site_id + market + kw_key) -> KI Gap Rows -> Save KI Gaps (upsert site_id + gap_id)
Shared end:   KI Cache Rows -> Save KI Cache (seo_cache upsert key: ki:* and serp:*) -> KI Run Row -> Save KI Run -> KI Report
  -> Ledger Settle (KI) via DFS Balance End / Load Run Ledger -> Settle Run Ledger -> alert sweep;  KI Report + settle -> Ledger Join -> Callback Ledger
  -> Has Callback (KI)? -> POST KI Report (body + run_ledger)
```
Each `[Run X + gate]` is `dfs_gate.splice`: `X -> X Retry Plan -> Any X Retries? -> Wait -> X (Retry) -> X Answers` (every answer through
`SU.fixAnswer`). Seven gated DataForSEO calls, all multi-item with NO node-level retry (N3); the two free GETs and the callbacks follow
retry_lint (callbacks on `retry_lint.ALLOW`: `POST KI Report`, `POST KI Refusal`, `POST KI Started`).

Node sources: `v5/code/KI_*.js`; the worker's I/O kit `v5/code/_ki_io.js` (KIW: market, seeds, request shapes and prices, ki:* cache keys
and lifetimes, answer parsing, SERP readings, table rows exactly the columns, sections, callback bodies). Kits inlined per node in this
order: COUNTRIES (Gate), `_fit_gate.js`, `_competitors.js`, `_kw_inputs.js`, `_site_model.js` (Research Result), `_dfs_retry.js`,
`_serp_cache.js`, `_serp_url.js`, `_ki.js`, `_ki_io.js` (E1 note 1: the fit gate and CMP before KI).

## 3. Money

- The plan prices every request it may send (`KIW.PRICE`, R5 prices) assuming every results page is a day-cache miss, and holds the
  estimate under the quote (`_cost_cal.js` DFS_EST: competitors $0.35, keyword_research $0.90). A competitor profile (ranked keywords,
  $0.048) that does not fit waits for the next run and the `profiles` / `competitor_keywords` section says so. The reservation is that
  estimate (`est_dfs_usd`); the settle takes the measured cost of the seven gated calls (`MEASURED = '!<the seven Answers nodes>'`, each task
  once by id); `seo_ki_runs.cost_dfs_usd` and the callback's `cost_measured_usd` carry the same figure. No model is called ($0 Claude).
- Lifetimes (KI.CONFIG.ttl_days): ranked keywords / sizes / rival overlap / the gap 7 d, referring domains 7 d, homepages and sitemap pace
  14 d, discovery lists and volumes 30 d, results pages 1 d (the shared `serp:*` day cache). `ki_force` ignores the ki:* lifetimes, never
  the day cache. Keys: `ki:<site_id>:<what>:<market>:<arg>` (kind `ki`, loaded by `kind = ki AND site_id`).
- Measured on the fixtures (fake DataForSEO billing every request at R5's prices, KIE2-4 / KIE2-8):

| Run | Estimate | Measured | Requests |
|---|---|---|---|
| competitors, techand-like, first run, nothing chosen (20 seeds) | $0.1276 | **$0.1029** | 24 |
| keyword research, techand-like, 2 chosen competitors | $0.6632 | **$0.3659** | 75 |
| either, repeated inside the lifetimes | - | **$0.00** | 0 |

  A competitors run with 3 chosen competitors adds up to 3 x $0.048 of profiles; 5 chosen would pass the quote on a first run, so the
  last ones wait for the next run (owner option: quote ~$0.55 to profile five at once).

## 7. Deviations, and why

1. **No Claude.** The design allows Haiku as a class / stage tie-break; KI's rules plus the homepage words reach E1's accuracy bars without
   it, so it is left out (no cost, no untrusted text in a prompt). A class under 0.6 confidence is `needs_review`.
2. **Homepages are read with a plain GET** (public hosts only, the address built from the host alone), not the Jina reader: every Jina
   reader node must carry the W07-A fallback chain (scenarios_w07a.js), and a homepage's words are all classification needs.
3. **Page-intersection rows are cut to the top 10 after the answer**, not by a server filter: `intersection_result.$page.rank_group` is
   listed by `available_filters` but not confirmed live (R5 §13 C4). Cost is capped by `limit 500` ($0.072).
4. **Traffic potential only for exact #1 addresses**: a breadcrumb-recovered address is approximate, so it is not sent (section says so).
5. **Gaps without a results page** use the provider's stored positions of the chosen set (labelled `exact: false`), so a gap row exists
   for keywords that got no live read.
6. **No ki_mode `trial` / `on` difference inside the worker**: both run; who sees the results is the app's rule (CONTRACTS section 1).
7. The worker reads seo_ki_competitors and seo_ki_gaps (its own state) but never seo_ki_keywords, so the new gate_lint pair has no reader yet.
