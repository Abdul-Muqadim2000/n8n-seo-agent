## 1. E1: a run cannot pay twice

**The rule.** Every key a run sends is recorded in its state row **before** the request leaves. AI Requests never sends a recorded key
again, whatever happened to its answer.

**Flow in the tracker** (`build_monitors.py`, section 1). The old link `Any AI Requests? -> Run AI Requests` now goes:

`AI Asking State` -> `Any Asking State?` -> `Save Asking State` -> `AI Requests Go` -> `Go AI Requests?` -> `Run AI Requests`

- `AI Asking State` (`v5/code/AI_Asking_State.js`, new) writes the state row `seo_cache ai_run:<site_id>` with:
  - this part's keys added to `asked_keys`;
  - `pending` = this part (its keys, execution, time, estimate);
  - `committed_dfs_usd` = the money spent so far plus this part's estimate.
- `Save Asking State` upserts on `key`.
- `AI Requests Go` (`AI_Requests_Go.js`, new) passes AI Requests' items through unchanged and in order, but only when every state row
  came back from the save. Otherwise it returns `skip` with `not_recorded`: nothing is paid, and the hand-off raises an ops alert.

**AI Plan** (`v5/code/AI_Plan.js:154-191`):
- `doneKeys` = the keys stored **plus** every key in `asked_keys`.
- `lostNow` = the `pending` keys that have no stored answer. A pending part is one that never reached its hand-off.
  - First loss in a run: the lost keys are counted as could-not-be-read (`chunk.lost_now`, `lost_total`, `lost_note`), they are never
    asked again, the next part is halved, and a `lost_part` ops alert (high) is raised.
  - Second loss: the run **stops** (`stop.status = 'failed_store'`).
- A state written before `asked_keys` existed falls back to the audit's count guard: stored < 90% of asked means stop.
- A stopped plan item asks nothing (`prompts: []`, `chunk.size 0`, `final_expected: null`, `est_dfs_usd 0`). Its ledger key is the job's
  own key (`null` is not a part), so the cycle job settles and the dispatcher does not retry into it.

**AI Chunk Handoff** (`v5/code/AI_Chunk_Handoff.js:60-100`):
- It counts the rows `AI Answer Rows` handed to `Save AI Answers` against the rows the insert returned. A shortfall or an error means
  **stop** (`failed_store`), with the reason naming the Data Table size limit.
- After this part's measured money, a run at its ceiling with requests left also stops (`stopped_ceiling`).
- Every stop produces:
  - `alerts`: exact `seo_ops_alerts` columns, severity `critical`, `next_attempt_at` = now;
  - `notices`: a `rejected` callback to the run's own caller when the run is on demand;
  - no `next`.
- The new state carries `asked_keys`, `pending: null`, `chunk_wall_s`, `sec_per_request` (measured only from parts of 2 minutes or
  more), `last_size`, `lost`, `lost_parts`, `stop_reason`, `ceiling_dfs_usd` and `committed_dfs_usd`.
- After `Save Run State`, `Run Alert Rows` -> `Save Run Alert` records the alerts (upsert on `alert_key`). The execution's existing alert
  sweep, which runs behind the ledger settle, delivers them to `SEO_ALERT_WEBHOOK_URL`.

**Stopped runs block the site.** `AIP.stateVerdict` returns `blocked` for `failed_store` / `stopped_ceiling` / `stopped` until the run is
older than `resume_days` (6). AI Plan then skips the site with the reason. The pulse's resume, cycle retries, catch-ups and on-demand
starts therefore never pay again. A person clears the row `ai_run:<site_id>` to let a new run start (the alert says so).

**Money ceiling.**
- `AIP.runCeiling(estimate) = min(max_run_usd $150, max($2, 1.5 x the run's own DataForSEO estimate))`. It is fixed in the state at the
  run's start.
- It is checked against `max(spent_dfs_usd measured per task, committed_dfs_usd)` in three places: AI Plan, the hand-off, and AI Requests.
  AI Requests stops adding requests per site at `chunk.ceiling_left_usd` and counts the rest in `chunks[].capped_by_ceiling`.
- The reservation is `min(run estimate - max(spent, committed), ceiling - committed)`. A dead part's committed money counts as spent.

**Run state shape** (`seo_cache` `ai_run:<site_id>`, `value` JSON). The fields added by F2 are marked `*`:
```
{ run_id, run_kind, on_demand, full_due, request_id, email, callback_url, cycle, site_id, domain, started_at, updated_at,
  chunk, status: running|done|failed_store*|stopped_ceiling*|stopped*, finishing, stop_reason*, asked, total, left, unavailable,
  lost*, lost_parts*, halve_next*, last_size*, chunk_wall_s*, sec_per_request*,
  spent_dfs_usd, committed_dfs_usd*, ceiling_dfs_usd*, spent_ai_usd,
  asked_keys*: { <prompt_id>: "<engine codes>" }   // c chatgpt, g gemini, p perplexity, l claude, o ai_overview, m ai_mode, b copilot, C chatgpt_api, G gemini_api
  pending*: { chunk, execution, at, n, est_usd, keys: {packed}, db_views } | null,
  executions, resumed }
```
`AIP.packKeys` / `unpackKeys` keep a 500-question run at about 14 KB.

**Proof.**
- F2-1 is the audit's `p_chain`: 4 starts with every save failing. 325 keys are paid once; part 1 stops with `failed_store` and a
  critical alert; starts 2 to 4 ask nothing and say why.
- F2-2: a part dies after storing half its answers. The resume asks none of the keys sent, counts the lost ones, halves itself and
  alerts. A second death stops the run. No key is paid twice across 5 executions.
- F2-3 covers the ceiling stop, the cap $0.05 under the ceiling, and a record that could not be saved (nothing is paid).
- S202 still asks every one of its 2,495 keys exactly once.

## 2. E11: the answers are stored before the analyst, and parts are sized by time

**New order:** `Parse AI Answers` -> `AI Answer Rows` (new) -> `Save AI Answers` (insert, moved) -> `Analyst Jobs` -> Answer Analyst ->
`Apply Analysis` -> `AI Analysed Rows` (new) -> `Update AI Answers` (upsert on `run_id + prompt_id + engine`, only the rows the analyst
changed) -> `AI Chunk Handoff`.
- Both new nodes write exactly the columns of `ladder_common.AI_ANSWERS_COLS`. The build writes them in as `__AI_ANSWERS_COLS__`, so a
  column F1a adds reaches them automatically.
- An answer the in-200 gate could not read is stored with its error and never as a measured "not named".

**Time budget** (`_ai_panel.js` 6c, `AIP.chunkPlan`):
- A part may use 40 of the execution's 60 minutes. From that come 300 s for loads and writes, the 20 s retry pause, and 30 s per analyst
  job (`chunk.analyst_jobs_max`, which Analyst Jobs now respects).
- The requests that fit are counted at the engines' slow-case seconds divided by the batch of 10, plus 15% for retries. Once a part of
  the run has measured its own seconds per request, the next part uses that figure plus 20%.
- The size is never more than 600, never less than 40, and halved after a lost part.
- AI Plan's execution loop shares one time budget across a multi-site execution.
- The six default weekly engines give **325 requests** a part, against 600 before: a 500-question run takes 8 parts, not 5.
- `chunk.size_basis` says how the size was set.

**Not fully done:** the audit asked that "the analyst can run on stored answers in the last chunk". The answer text is not stored (only a
520-character excerpt), so a part that dies after its save but before its analysis keeps the parser's reading for those answers. The
next part says so (`chunk.unanalysed`, `unanalysed_note`). Re-reading them would need the text stored or the excerpt fed to the
analyst. That is left open.

**Proof.** F2-6 walks the generated connections (exported by the build to `harness/ai_vis_wiring.json`):
- `Save AI Answers` reaches the Answer Analyst, and the analyst never reaches the insert.
- `Run AI Requests` cannot be reached from AI Requests without passing `AI Requests Go`.

## 3. E2 / E15: question ids

- One normal form for every script (`AIP.normQ`): NFKC, lower case, Arabic harakat and tatweel removed, anything that is not a letter,
  digit or mark becomes a space.
- `AIP.promptId(site_id, prompt) = 'q_' + hash64(site_id + '|' + normQ(prompt))`, 16 characters.
- `hash64` is two independent 32-bit mixes (cyrb53's multiply-xor mixing, both halves kept), so 64 bits. It is built on `Math.imul`, not
  BigInt, and was tested in the 2.41.4 container's Node.
- Old `p_` ids stay readable. `AIP.findStored` lets a stored row with the same normal form keep its id, so an owner re-adding a stored
  question does not create a duplicate.
- **Save Prompts** (`build_monitors.py:374`) and the Site Admin's **Set AI Prompts** (`build_site_tracker.py`) now upsert on
  `['site_id', 'prompt_id']`.
- `Prompt_Rows.js` dedupes new questions against **every** stored row of the site, whatever its status. A question the owner switched off
  or the gate refused is never written again under a new id.
- `AI_Prompt_Rows_Admin.js` inlines the same kit (`build_site_tracker.py` now replaces `/*__AI_PANEL__*/`).
- **App pinning.** The app sends ids it read from the table (`app/server/src/routes/sites.ts:400`: `edit[].prompt_id`, `pin` / `unpin`
  as ids or texts). Admin still finds rows by id or by normal form, and a reworded question still becomes a new id with the old row
  switched off. No app change is needed.
- **Proof** (F2-4):
  - 3 Arabic writer questions give 3 rows and 3 `q_` ids;
  - Cyrillic and Chinese questions get distinct ids;
  - case, spacing and harakat do not change an id;
  - two sites get different ids for the same question;
  - an Arabic question has the same id on the writer's path and the owner's path.

## 4. E9: the search phrase

- `AIP.keywordOf(question)` keeps the content words in their own order, at most 6. It drops question words, English and Arabic stop
  words and filler, keeps hyphenated words and "IT" whole.
- Example: "What should I check before choosing an e-invoicing provider in the UAE?" gives "choosing e-invoicing provider uae".
- The owner may give their own phrase: Admin Action passes `keyword` on `add` and `edit`.
- New column **`seo_ai_prompts.keyword_source`**: `owner` | `writer` | `template` | `derived`. It is in `ladder_common.AI_PROMPTS_COLS`;
  `sync_tables.py` adds it on deploy.
- AI Requests does not ask Google's AI Overview for a `derived` phrase, so AI Overview presence is measured on real search phrases only.
- **App follow-up (not done here).** The CSV import / panel manager would need to send `keyword` per question. `shared/src` schemas may
  strip the field.

## 5. E12: scoped loads

- Every read of a per-site AI table in the tracker now filters server-side with `site_id like <scope>`:
  - AI Prompts;
  - AI Visibility, plus a 60-day window;
  - Link Prospects;
  - AI Daily, plus 15 days;
  - Cache (AI), plus kind ai;
  - Query History, plus 35 days;
  - Pages (AI);
  - AI Run Answers, plus `run_id like <continue_run>`, `run_kind != pulse` and 6.2 days.
- `like` is n8n's "contains" with `_` escaped (checked in the 2.41.4 source: `escapeLikeSpecials`; a value containing `%` is used as
  given).
- The scope comes from the trigger: its `site_id`, else `site_<domain>`, else `%` (a start that names no site reads every site, as
  before). AI Plan still filters exactly.
- The date windows are the caps; there is no row cap, because a silent truncation would break rule 1.
- The pulse (which serves every site) and AI Growth / Backlinks / Link Builder were **not** scoped. Their loads of `seo_ai_visibility`
  remain whole-table. Left open.
- **Proof** (F2-6): every scoped node carries the filter, and the scope expression evaluates correctly for a site id, a URL-shaped
  domain, and nothing.

## 6. E17: open-run notices

- An on-demand start that meets an open run (busy, resumed by this start, or stopped) adds a notice to the plan.
- Two new chains post it at once, each a code node, an IF and an HTTP POST with 3 tries and continue on error:
  - `Open Run Notices (AI)` on the run's path, after `Any Sites (AI)?`;
  - `Busy Notices (AI)` on the nothing-to-do path, before `Nothing To Do (AI)`.
- **Callback body** (the app's existing `rejected` contract):
  `{stage:'rejected', status:'rejected', reason:'open_run', skipped:true, error:<sentence>, request_id:<caller's>, open_run:{run_id, status, part, asked, total, started_at, updated_at, expected_finish}, cost_usd:0}`.
- A run that continues now always keeps **its own** caller (request id, callback, e-mail from the state). Before, an on-demand resume
  took over the open run's callback.
- A scheduled start posts nothing.
- `Stop Notices (AI)` posts a stopped on-demand run's notice to its own caller (`reason: 'run_stopped'`).
- **App follow-up.** The app closes such a request as failed with the sentence. It could render `reason: 'open_run'` as "part of the open
  run" instead.
