## 1. Fan-out ranking gap (`ai_fanout_check` N, default 0 = off; MARKET_RND gap 4)

- **What it does.** In the run's LAST part, after the week is measured and stored, the searches the engines ran before answering are
  deduplicated (case, quotes, spacing; W2-E1's `fanout_json` per answer is read when present, else the stored `fanout`), ranked by how
  often they ran (then by how many engines), and the top N are checked on Google's top 10 (`serp/google/organic/live/advanced`, depth 10,
  the site's market: the rank tracker's request shape at the depth this needs).
- **One reading per search per day.** A results page this site's paths read earlier today (`seo_cache` `serp:`, the shared SC kit,
  `Load SERP Cache (AI)`) is reused for nothing; every page read now is stored there for the other paths (`Extras Cache Rows`).
- **Per search** (`fanout_gap_json.queries[]`): `query, freq, engines, our_rank|null, our_url|null, target_url|null, top_domains, cited`, plus
  `cited_n`, `gsc` (the site's Search Console row for the exact or a close query: impressions, clicks, position), `read` (read now / a
  reading of today / not read) and `flag`: `ranks_not_cited` (we rank #1-3 and no answer that ran the search cited us; also listed in
  `ranks_not_cited[]`), `cited`, `ranks`, `not_in_top10`, `not_read` (a page that failed twice behind the in-200 gate is never "not in the top
  10").
- `target_url` = the inventory page (`seo_pages`, a page answering 4xx left out) whose address, title and H1 share most content words with the
  search (>= a third of them); `cited` = an answer that ran the search cited one of our pages.
- Row-level: `checked_n, distinct_n, top_n, setting, cost_usd, from_reading_today_n, not_read_n, not_in_top10_n, location_code,
  language_code, as_of, method`. The report has a "Do you rank for what AI searched?" table and a line for "ranks top 3, not cited".

## 3. Persona effect (`ai_persona_context`; MARKET_RND gap 7), labelled "API answers"

- 12 questions (`AIP.PERSONA.questions`, = the minimum for a rate) spread over the panel's topic clusters, the SAME for every role, asked
  of the ChatGPT API (`chat_gpt/llm_responses/live`, gpt-5.4-mini, web search, the site's country) once with each buyer role as
  `system_message` ("The person asking you is a CFO at a business in United Arab Emirates. Answer their question as you would answer that
  person.") and once with none: one control arm shared by every role, so the cost is (roles + 1) x 12 answers a weekly run.
- "Named" is read by the entity kit (AIE) over the site's own names. Per role: named rate with and without, the change, a two-proportion
  z-test (|z| >= 1.96; under 12 answers a side "too few answers"; a null result printed as "no measurable difference"), and the same pooled
  over the stored runs of the last 28 days (`notes_json.persona` of earlier rows).
- The interval: each change carries its 95% interval (Newcombe's hybrid score method, the two Wilson intervals combined), and a role's effect
  is real when that interval excludes 0 (the z of the two-proportion test is reported beside it).
- **`persona_effect_json`** (W2-A's contract addition, its own column, written by the row update): exactly
  `[{ role, with: { rate, n }, without: { rate, n }, delta, lo, hi, significant }]`, rates and the interval in points 0-100, the 28-day pooled
  figures (this run included; a site's first run is that run alone).
- Also kept in `notes_json.persona` (the per-run and pooled detail the next run pools from), in the callback (`persona_effect`) and in the
  report under "Does the asker's role change the answer? (API answers)". Kept out of every headline figure.

## 4. Demand as a range (MARKET_RND gap 9) and the owner's AI reports (gap 10)

`demand_json` = `{ questions: [{ prompt_id, proxies: [{ source, value, as_of, note }], lo, hi }], questions_with_proxy, questions_total, cut,
market, market_carried, note, as_of }`. Per question, every proxy we hold, each with its source and date:

| source | value | from |
|---|---|---|
| `ai_keyword_volume` | AI searches a month of the question's search phrase | the stored `volume` (DataForSEO AI Keyword Data, from People also ask); `as_of` = the row's date |
| `llm_mentions_question` | the AI-answer database's volume of the same question (stems Jaccard >= 0.6) | this execution's discovery / "questions citing you" reads; Google AI Overview data outside US-English, said so |
| `search_console_impressions` | impressions of matching question queries, 28 days scaled to a month, a floor | `seo_query_history` (this site only) |
| `search_console_ai_upload` / `bing_ai_upload` | AI Mode / AI Overview or Bing AI impressions of matching queries in the owner's uploads | `seo_ai_imports` |

`lo` / `hi` span the proxies a question has; a question with none has no range (never 0). The 200 questions with the highest figure are
kept. The monthly **market trend** (`ai_demand_market`, full run): `historical` (mentions and their AI search volume month by month for the
domain), `timeseries_new_lost` (mentions won / lost a month, 6 months), `top_mentioned_brands` (the 10 brands AI names most for the main
topic); platform `chat_gpt` for US-English sites, `google` elsewhere, and the note says the ChatGPT part is US-English only. A weekly row
carries the last trend read, with its date (`market_carried`). A failed task is named with its reason, never an empty leaderboard.

`imports_json` (free, written with the row; '' when the site uploaded nothing for the period). Rows of other sites and rows older than 28
days are left out. **The exact shape written** (every key always present when the object is; a source is present only when it has rows):
```
{
  "period":  { "from": "YYYY-MM-DD", "to": "YYYY-MM-DD" },                 // the 28 days ending on the run's day
  "sources": {
    "bing_ai" | "gsc_ai": {
      "rows": n, "days": { "from": "YYYY-MM-DD", "to": "YYYY-MM-DD" },    // first / last day present in the rows
      "impressions": n, "citations": n, "clicks": n,                       // sums over the rows
      "urls_n": n, "queries_n": n,
      "top_urls":    [{ "url", "impressions", "citations", "clicks" }],    // 10, most citations then impressions
      "top_queries": [{ "query", "impressions", "citations", "clicks" }],  // 10, same order
      "files": ["file_name", ...],                                          // up to 5
      "imported_at": "ISO"                                                   // the latest upload
    }
  },
  "copilot": null | { "source": "bing_ai", "citations": n, "impressions": n, "urls_n": n, "as_of": "YYYY-MM-DD",
                      "label": "from Bing Webmaster (your export of YYYY-MM-DD)", "note": "..." },
  "note": "Your uploaded reports, <from> to <to>: Bing AI Performance (n rows, <from> to <to>); Search Console AI Mode / AI Overviews (...)"
}
```
`copilot` is the Copilot figure's ground truth whenever a Bing file exists (its `label` is the line the tile prints).

## 6. Where it runs, and the money

The tracker's last part, after `Save AI Visibility` and the run's `done` state (`Save AI Cache`), so a part that dies in the options can never
make the run ask its questions again and the week is already stored:

`Prune Old Answers -> Prompt State Rows -> Any Prompt State? -> Save Prompt State -> AI Extra Requests -> Any AI Extra Requests? -> Run AI Extra
Requests [in-200 gate] -> AI Extras -> Extras Vis Rows -> Any Extras Vis? -> Update AI Visibility (Extras) -> Extras Cache Rows -> Any Extras
Cache? -> Save Extras Cache -> AI Brief Input`.

- One paid HTTP node for the three options, behind the in-200 gate (no node-level retry: retry_lint's paid rule), so a task error inside a
  200 is re-sent once and a twice-failed one is "not read".
- **F2's money ceiling holds:** AI Extra Requests adds the options in the order trend, fan-out, persona only while the run's measured
  DataForSEO money (AI Metrics' `vis_row.cost_usd`, every part) plus their estimate stays under the run's ceiling; what does not fit is named
  in `notes_json.ceiling_note`, never asked.
- **The ledger:** the reservation includes the options (they are in `AIP.cost`); the settle reads `AI Extras` (`measured =
  'AI Metrics|AI Chunk Handoff|AI Extras'`): each task once by its id across both attempts. The stored row's `cost_usd` grows by the
  options' money (the update).

### W2-E2's Sentiment Reader in the cost model (coordinator's request)

The Sentiment Reader (Claude Haiku, W2-E2, merged) reads every answer that names the business, 20 a call, at most 40 calls a run, about
$0.012 a call. `AIP.cost` / `estimateAiPanelCost` now add `sentimentOf(weekly answers)` to every run's Claude money: named answers = the
weekly run's answers x **50% (ASSUMPTION, `FIXED.sentiment_named_rate`)**, deliberately high (a new site is named in far fewer answers, so the
quote is an upper bound); calls = ceil(named / 20), at most 40. The full run's few extra answers (Claude monthly, the brand question) are inside
that margin and not priced separately, so a quote does not move by a call with the engine set (the app's "Claude only on the monthly full run"
test holds). **This is a default cost change** (it is W2-E2's reader, on by default): 50 questions +$0.36 a month (7 calls, $0.084 a run),
200 questions +$1.30 (25 calls, $0.30 a run), 500 on all engines capped at 40 calls ($0.48 a run). Every `cases` golden value with Claude money
moved accordingly; both sides regenerated (`FIXED.sentiment_*` in the table, harness W2E3-5, app 621 / 621).
