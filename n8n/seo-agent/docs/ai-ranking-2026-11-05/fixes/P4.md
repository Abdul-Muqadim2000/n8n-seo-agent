## 1. What is built

### The setting

The setting has five fields: `ai_rank_mode` (off / shadow / on), `ai_rank_reserve`, `ai_rank_fanout_n`, `ai_rank_mentions` and `ai_rank_brave`. Every field is off when empty.

- **`_monitor_sites.js`** now inlines AIRF and sets `settings.rank = AIRF.settingsOf(m)` on every monitor site.
  - No plan, report, callback or row copies `settings` whole. AP1 checks this.
  - The one exception is internal. `Audit Candidates` hands `settings` on to the Audit Scheduler's own nodes, and `Audit Schedule Plan` builds the audit's body field by field.
- **Site Admin `monitors`**:
  - `Admin Action` runs `AIRF.validate`. A bad value is refused with its reason and nothing is stored. A good value is handed on normalised.
  - `Monitor Row (Admin)` sets a value that was given. `''` clears it to null. A field that was not given keeps its stored value.
- **"Track my site"** (`Monitor_Row_Track.js`, W0's lines) never changes the five fields, even when its body asks.
- **Turning a site on or off** is done with Site Admin `monitors`. To stop every site at once, set the `seo_cache` row `air:kill` = `1`.
- **`ai_rank_reset.py --site <id> [--purge-air] [--apply]`** clears what an `on` period leaves behind: the `core_until` stamps and the protect row. With `--purge-air` it also deletes the site's AIR history. It is a dry run by default.

### The AI Growth side branch

The wiring is in `ai_rank_wiring.py`. Every AIR node has `onError: continueRegularOutput`.

1. `Any Growth Row?` (false) and `Save AI Growth` both lead to **`AI Rank Gate`**, then **`Any AI Rank?`**.
   - With every site off, these two nodes are the only AIR nodes that run.
   - The gate reads `Growth Plan` and `Load Monitors` and uses `AIRF.settingsOf`.
2. The kill switch comes next: `Load AI Rank Cache` (kind `air`), `AI Rank Live` and `Any AI Rank Live?`.
3. The five `Ensure AI Rank … Table` nodes run.
4. Twelve loads follow:
   - AIR questions, actions, sources, priors, and runs from the last 84 days
   - Index pages
   - The SERP cache
   - AI daily rows from the last 60 days
   - AI answers from the last 28 days
   - Listings, outreach and prospects
   - Each load is scoped to the site, except the priors (shared by every site) and the SERP cache (stored with an empty site id).
5. `ai_rank_requests_wiring.wire_requests` (P5) runs, then **`AI Rank Plan`**.
6. Eleven builders follow. All of them run the same source, `AI_Rank_Rows.js`, with the table and its columns baked in. Each builder has an IF and a save:

   | Mode | Builders |
   |---|---|
   | Shadow and on | run, question, action, source and prior rows |
   | On only | target, prospect, proposed question, `core_until`, protect cache and growth patch rows |

   The on-only builders return `[{ skip: true }]` for a site in shadow. The plan also builds no sink rows in shadow, so two guards stand in the way.
7. `Prune AI Rank Actions` / `Prune AI Rank Sources` remove expired actions and sources unseen for 120 days.
8. **`Growth Report`** runs, exactly once.

**What `AI Rank Plan` does:**

- **Kit calls.** It calls ARD and ARL through the frozen signatures, with the extra inputs listed in P1.md and P2.md:
  - One answers array and one units array is passed to every ARD call.
  - 28 days of answers go to the source graph.
  - `demand` has the `{ byPrompt, candidates }` shape. The candidates come from the gated ladder keywords and the Search Console queries.
  - `assignArms` gets `site_id` and `holdout_days: 84`.
  - `choose` gets `{ now, units60 }`. ARL's default capacities apply in both shadow and on, so the shadow plan is what on would do.
  - `outcome` and `learn` get the `{ action, outcome, happened }` items.
- **Read-path gates:** `FITR.rungs` for ladders and `OK.sellsSame` for prospects and outreach rows.
- **Gate on the way out:** a placement on a competitor's own page, or on a client page, is refused. Rival lists are learn-only.
- **Old logic:** the current logic's choice from this run (Growth Plan targets, Earned Media pages, Growth Metrics actions) is stored in `old_json`.
- **Status exits** (INVARIANTS rule 4):
  - verified / done / not_happened come from the outcome
  - shadow and open actions become `expired` after their window + 14 days
  - expired actions are pruned after 120 days
- **Missing kits.** A kit that answers `unavailable` is named on the run row (`kit not built: …`), and nothing computed from it is written.
