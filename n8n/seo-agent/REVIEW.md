# SEO Agent — engineering review and v4 upgrade

Reviewed: workflow **SEO Agent v3 — Audit, Keywords, Verdict & Content** (`uMY3xr66Q7aLX9uA`, 134 nodes) on the local n8n 2.41.4 instance.
Delivered: **SEO Agent v4** (`SEOagentV4Full01`, 191 nodes after the v5 methodology upgrade and live-test fixes; 312 after v4.2-v4.4), **SEO Agent — API** (`SEOagentAPIentry`, the webhook front door) and **SEO Agent — Error Handler** (`SEOagentErrHandl`), all imported inactive. v3 was not modified.

## 1. Verdict in one paragraph

The product design is strong: five clear modes (keyword content, keyword discovery, site description, technical audit, full SEO report, plus an API), grounded in real data (DataForSEO SERP/Labs/On-Page/Backlinks/LLM Responses, Jina Reader, PageSpeed) with well-written Claude prompts, deterministic QA of the generated copy, and a scored, sectioned Word report. The engineering had real defects that would have shown up on the first customer run: the API path never returned a response, the copywriter model was capped at 4,096 output tokens, one regex reduced the brand name to a single letter, sites that redirect apex to www were flagged as duplicates, one 404 page capped any site at 60/100, and validation errors crashed the run instead of telling the user what to fix. All of these are fixed in v4 and verified by an offline harness that executes every Code node in the real Node runtime. The one thing that cannot be verified from here is a live run: **no node in v3 or v4 has credentials attached**, so the workflow has never executed on this instance.

## 3b. Why the keywords were ordinary and the content read generic — and what v5 does about it

**Keyword discovery (v3/v4).** One `keyword_ideas` call ordered by search volume, from 12–15 seeds, scored as volume × (1 − difficulty) × intent weight. That is why the output was the obvious head terms: volume ordering surfaces "what is erp" and "erp software", no long-tail or related-search sources were used, competitor rankings were ignored, relevance was never checked (so "erp course" or "erp salary" survived), and nothing accounted for SERP features that take the clicks or for commercial value.

**v5 discovery pipeline.** Seeds are generated by buyer motive (services, problems, comparisons, pricing, local, audience). Seven data pulls build one pool: keyword ideas in relevance order with SERP-feature data, long-tail suggestions for the 3 main seeds, related searches (depth 2) for 2 seeds, a live SERP for the primary seed, then the keywords the 3 closest competitors rank for (top 20). Each keyword gets an **opportunity score** = traffic potential (volume after AI-Overview / snippet / video / local-pack click loss) × winnability (difficulty and top-10 link strength) × commercial value (CPC) × intent weight for the client's goal × trend. The top 240 are screened by Claude for **relevance** (2 core, 1 adjacent, 0 drop), intent, page type and a topic label; labels form **clusters** with Now/Next/Later tiers and a suggested page per cluster. The 8 priority keywords are live-checked on Google (who ranks, your position, features), and **AI search demand** (DataForSEO AI keyword data) is shown next to Google volume. The report is a content plan, not a keyword dump: priority cards with "why", topic plan, quick wins, buyer questions, competitor gaps, long-tail, AI demand, by intent, methodology.

**Content generation (v3/v4).** One prompt wrote the whole page from a brief built on 4,500-character competitor excerpts and headings, with no facts about the client beyond a one-line description, no verified external facts, and a QA that only checked structure. The result had to be generic: every specific became a placeholder, and nothing stopped filler ("seamless", "robust", "in today's fast-paced world").

**v5 content pipeline.** The client's own pages are read (existing page on the topic, homepage, one service page) and trust signals extracted, so the copy uses real facts. Competitor pages are kept at 9,000 characters and distilled into a **term model** (phrases the top pages share), the questions they answer, and the statistics they cite. A second search collects **verified facts with source URLs** (authority-ranked). The analyst now also returns information-gain opportunities, reader questions, winning formats and trust signals. The verdict sees the client's **site authority** and estimates expected visits and time to rank. The brief adds pain points, objections, information gain, an evidence plan, terms to use with counts, snippet targets with 40–60-word answers, client facts, proof elements, title/meta variants and voice rules. The copywriter (Claude Opus 5.5 with adaptive thinking) works under explicit rules: two specifics per section, a banned-phrase list, active voice and sentence-length limits, numbers only from the evidence plan with a linked source. A **critic** (Sonnet 5.5) scores the draft and writes revision instructions; the deterministic QA computes a **content score** (structure 25, topic coverage 25, readability 15, specificity 10, clean language 10, length 15), detects clichés, readability, passive voice, term coverage, unanswered snippet questions and unsourced numbers; the editor (Opus) fixes everything in up to two rounds. The report shows the score breakdown, topic coverage table, sources cited, title/meta alternatives and the editorial review.

**Cost and time per run (estimates).** Keyword content run: about 9 DataForSEO calls and 6–7 Claude calls (3–4 on Opus); roughly $0.70–1.20 and 8–14 minutes. Keyword discovery: about 13 DataForSEO calls (incl. AI demand) and 4 Claude calls; roughly $0.40 and 3–5 minutes. Opus pricing is $4/$20 per million tokens, Sonnet $2/$10.

## 3c. Keyword ladder (v4.2, 2026-10-01)

**Why.** Google ranks a head term for the site with the most complete, trusted coverage of the topic. One page rarely gets there; a *ladder* does: several specific long-tail pages (lower rungs) that link up to one strong page for the head term, plus links from other sites over time. The new mode plans that ladder from data, writes the first rung now, registers the ladder for weekly tracking and tells the user when to move up. Decisions taken with the user: weekly tracking, recommend-only (no automatic next rung), n8n Data Tables as the store, one page per run, WordPress off.

**Mode "Rank my site for a keyword" (form) / `mode: "ladder"` (API).** Inputs: destination keyword, domain (required), country, business, customers, facts, goal, tone, CTA, pages to write now (1-3), e-mail and/or callback. The run reuses the keyword pipeline on the head term up to the **Verdict** (sitemap, client pages, SERP, competitor analysis, keyword data, site authority), then branches at *Ladder Mode?*:

1. **Ladder Requests / Run Ladder Research** — four DataForSEO Labs pulls around the head term: long-tail suggestions (500), related searches depth 2 (300), keyword ideas for the head term plus the site's services and the verdict's secondary keywords (400), and the keywords the domain already ranks for (500, top 60).
2. **Ladder Pool** — one pool with volume, difficulty, CPC, trend, SERP features and top-10 link strength; ideas and rankings must share a topic token with the head term (geo words ignored); the same opportunity score as discovery; current positions and ranking URLs per keyword.
3. **Ladder Relevance Chunks / Ladder Keyword Relevance** — the AI relevance screen (Sonnet 5.5, low effort), anchored on the head term: core (2) only when a page about the keyword would naturally link up to a page about the head term.
4. **Ladder Plan** — rungs by difficulty: rung 1 up to 25 (long-tail, 20+ searches), rung 2 26-45, rung 3 46-60, head term on top, harder keywords listed for later. One page per topic cluster (coarse AI labels are split by page type and capped at 6 keywords), 2-4 pages per rung, 8-12 pages in total; each page gets a primary keyword, supporting keywords, page type, traffic potential, current position and either an existing URL (sitemap token match or the URL that already ranks → "improve") or a planned URL ("new"). Internal link map: every rung page links up to the top page and sideways to one sibling; the top page links down to every rung page. Timeline in months (rung 1: 1-2, rung 2: 3-5, rung 3: 6-8, top: 9-12), shortened when the site already has authority or ranks for the head term. Feasibility from the verdict (winnable / stretch / unrealistic, alternatives for navigational or hopeless heads), plus what else is needed (referring domains vs the top-10 average, authority today, local trust signals, entity pages, publishing discipline).
5. **Build Ladder Report → PDF** — the Keyword Ladder Plan (summary, feasibility, the ladder per rung, link map, pages written now, requirements, tracking, later keywords, method), Word-compatible .doc plus PDF through Gotenberg.
6. **Ensure Ladder Table / Ensure History Table / Ladder Rows / Save Ladder Rows** — Data Tables `seo_ladders` and `seo_rank_history` are created on first use (Data Table node, "create, reuse existing"), one row per ladder page with status planned / writing.
7. **Ladder Delivery → Spawn Page Runs → Start Page Runs** — the first N rung pages start as separate executions through *API Entry* (`mode: keyword`, `force_content`, `ladder_id`, `ladder_rung`, `ladder_head`, `ladder_links`); each delivers its own PDF/Word by e-mail/callback. Ladder links (top page, sibling) are internal-link candidates even when they are planned pages, so the brief and the QA keep them; the verdict router never drops content for a ladder page. In parallel the plan goes out by e-mail (*Send Ladder Report*), download (*Download Ladder Plan*) or callback (`stage: ladder_plan`).

**Form completion pages end the execution (live finding, 2026-10-01).** When a Form node in "completion" mode renders its page (download, "started", validation error), the execution stays in *waiting* and any branch still queued never runs. Discovery follow-ups (keyword report / page content for the chosen keyword, site audit) and form-requested audits therefore run as **separate executions** through *API Entry* (*Spawn Follow-ups → Start Follow-up Runs*, *Spawn Audit Run → Start Audit Run*), exactly like the ladder's page runs, and every form flow ends with its completion node. The "Your audit has started" page now appears at once instead of after the whole audit; the WordPress gate is ordered before the delivery step for the same reason. API callers are unaffected (one callback per stage with the same request_id); the Rate Limit estimates are per execution (report-only keyword run $0.30).

**Discovery choice step (form only).** After *Build Keyword Strategy*, form users get a "Choose your keyword" page (JSON-defined dropdown: the 8 priority keywords as "keyword · searches/mo · difficulty · intent · page type", plus "Let the system choose for my goal"). *Apply Choice* replaces the pipeline keyword and the report's "Where to start" line. API callers keep choosing through `mode: keyword` / `mode: ladder`.

**Rank Tracker (`SEOagentTracker1`, weekly Monday 08:00, plus *Manual Run*).** Loads every ladder, skips ladders whose top page has held the top 3 for four checks, checks the Google top 100 for each page's primary keyword and the head term (DataForSEO SERP live, about $0.002 each; caps: 15 keywords per ladder, 120 per run), appends `seo_rank_history`, and sends one progress e-mail / callback per ladder: positions vs the previous check, rungs in the top 10 / top 3, drops of 5+ positions, and the recommended next rung with a form link and a ready-to-send API body.

**WordPress (`SEOagentWordPres`, optional, off).** Creates the finished page as a WordPress **draft** (title, slug, excerpt = meta description, HTML content with the internal links, JSON-LD blocks, Yoast/RankMath meta keys) through the REST API with the credential "WordPress (SEO Agent)". Enabled by `CONFIG.wordpress_publish` plus `wordpress_url` in the request; the sub-workflow must be published before use (n8n 2.x refuses to execute unpublished sub-workflows, live finding 2026-10-02).

**Testing.** Harness scenarios S7 (ladder: validation, API and page-run normalisation, ladder links as candidates, requests, pool, relevance, rung bands, link map, timeline, report, PDF, Data Table rows with exact columns, delivery, spawned payload round-trip, callback, store failure), S8 (tracker: plan, positions incl. failed check, history columns, first and second check with gains/drops, stop rule, no ladders) and S9 (WordPress payload), plus the choice step inside S4. 155 node runs, 0 failed. Sample output: `harness/sample-output/ladder-plan.doc.html`, `tracker-email.html`.

**Test tooling.** `SEO Agent — Test Runner` (`SEOagentTestRun1`, `POST /webhook/seo-test-run`, header credential "SEO API Key (test)") starts any SEO Agent workflow with a JSON body in the background (`workflow` picks the target); it bypasses the API front door's Quick Validate on purpose and should be deactivated or deleted after testing.

## 3d. Site tracking (v4.3, 2026-10-02)

**Why.** After the content and the ladder are live, the loop needs real outcome data, not one SERP sample: Search Console gives the true average position, impressions and clicks per query, GA4 gives visits and key events, Google Trends says whether demand is growing. Spec and decisions: `TRACKING_FEATURE_SPEC.md`.

**Mode "Track my site (rankings & traffic)" (form) / `mode: "track"` (API).** Inputs: domain (required), country, optional search terms (up to 20), optional GA4 property id, e-mail or callback. *Site Row (Track)* upserts the site into the Data Table `seo_sites` and *Start Site Tracker* runs the tracker at once (first report in about 3 minutes); the form ends on "Tracking is set up", API callers get `stage: site_tracker_setup`. Every domain with a keyword ladder is tracked automatically (virtual site, e-mail from the ladder), so the Rank Tracker's Monday 08:00 ladder e-mail is followed by the 09:00 performance report.

**Site Tracker (`SEOagentSiteTrk1`, weekly Monday 09:00 plus *Manual Run* `{ site_id | domain, on_demand }`).** One Google **service account** (credential `Google Service Account (SEO Agent)`, id `SEOcredGoogleSvc`, read-only scopes `webmasters.readonly` + `analytics.readonly`) is used by HTTP Request nodes; the owner adds its e-mail in Search Console (Full) and GA4 (Viewer). Per site: *GSC Sites* → *Resolve Properties* (sc-domain first, then a URL-prefix property, then the property named at registration) → *GSC Requests* (last 28 complete days ending 3 days ago vs the 28 before and the same 28 days a year ago: clicks by day, top 500 query×page rows, pages, each tracked keyword as an exact query with its ranking page, both periods) → *Parse GSC* (totals, deltas, winners / losers / new / lost queries, striking distance 4-20, CTR gaps under half the expected rate, page movers, decaying pages, tracked positions) → GA4 property **detected** from the web stream URL when no id was given (*GA4 Accounts* → *GA4 Streams*) → *GA4 Requests* (organic vs all channels for both periods, organic landing pages, organic sessions by day) → *Inspect URL* (Search Console URL Inspection: is each ladder page indexed, coverage state, last crawl, canonical) → *Google Trends* (DataForSEO, up to 4 head terms per site, 12 months: direction, peak, rising related searches) → *SERP Check (Site)* (live top 50 for the site's own keywords; ladder keywords are read from the Rank Tracker's `seo_rank_history`) → **Site Metrics** (KPIs, alerts, ranked actions with ready-to-send API bodies, exact rows) → Data Tables `seo_site_metrics` (one row per site per run), `seo_query_history` (tracked keywords + top 100 queries), `seo_sites` (upsert: resolved property, GA4 id, last run) → **Site Brief** (Claude Sonnet 5.5, low effort, ~$0.03 per site) → **Site Report** (HTML e-mail: headline + summary, alerts, connect-Google box, KPI tiles, "Do this week" with API bodies and the form link, tracked keywords with Search Console average vs live check, ladder index status, striking distance, CTR gaps, movers, pages, traffic, trends, watch list) → PDF (Gotenberg) → e-mail and/or callback (`stage: site_tracker`). Not connected = the report still runs (trends, live checks, ladder positions) and explains the two steps; every optional source is gated by an IF so a missing one never stops the spine.

**Site Admin (`SEOagentSiteAdm1`, published sub-workflow).** `{ action: delete | pause | resume, site_id | domain }` through the Test Runner or an Execute Workflow node: pause sets `status = paused` in `seo_sites` (weekly run skips it, on-demand still works), delete removes the row. No UI step needed.

**Guardrails.** 25 sites per run; per site 40 tracked keywords, 30 exact-query requests, 20 inspections, 4 trend keywords, 20 live checks. Google calls are free; DataForSEO about $0.015 per live check and $0.011 per trend keyword (measured live). The brief's model failure falls back to the deterministic actions; Data Table failures never fail the run.

**Verified live (2026-10-02)** with the real service account on techand.ai: see the test log (G1). **Testing.** Harness scenario S10 (track intake form + API, site row columns, tracker payload and store failure, plan with on-demand filter / virtual ladder site / paused site / no match, 28-day windows, property resolution incl. permission denied and URL-prefix fallback, every request builder and parser against API-shaped fixtures, metrics rows with exact columns, alerts and actions incl. not-indexed page, slipped keyword, striking distance with `existing_page_url`, CTR gap, decaying page, rising trend, report with and without the brief, callback bytes, the fully disconnected path). 206 node runs, 0 failed. Samples: `harness/sample-output/site-tracker-email.html`, `site-tracker-email-not-connected.html`.

## 3e. Content cadence, blog package and "I published a page" (v4.3, 2026-10-02)

**Decision with the user.** The agent delivers the blog content; the owner publishes it in whatever framework the site uses (no CMS integration needed). Blogs per week are configurable per site, and the owner reports each published URL so the trackers follow it.

**Blog package (every content run).** *Blog Package* (after *Attach PDF Report*) turns the generated page into a CMS-agnostic package: `<slug>.html` (clean semantic article with the JSON-LD blocks), `<slug>.md`, and `<slug>.meta.json` (title, H1, slug, suggested URL, meta description with lengths, primary / secondary keywords, page type, headings, internal and external links, schema blocks, word count, content score, publish checklist). Attached to the report e-mail next to the PDF/Word, and returned in the `content` callback as `markdown`, `html`, `meta`. Runs without content pass through untouched. Sample: `harness/sample-output/blog-package-*`.

**Image plan (2026-10-02, later the same day).** The strategy brief now specifies three images per page: a hero (also the featured and Open Graph image) and two in-body visuals, each with placement (the H2 it belongs under), purpose, subject for the designer or stock search, alt text (topic included, under 125 characters), optional caption and a kebab-case WebP file name. The blog package carries them as `<figure>` placeholders at the right sections (hero after the H1), as Markdown image lines, and in meta.json as `images`, `featured_image` and `open_graph` (og:image 1200×630, twitter:card); the PDF report shows the plan as a table. When a brief has no images, the package still proposes three slots from the headings. "I published a page" now also checks the live images: at least two content images, alt text on every image and the topic in at least one, descriptive file names (no IMG_1234), width and height attributes, WebP/AVIF for at least half, and an absolute og:image.

```bash
curl -s -X POST http://localhost:5678/webhook/seo-keyword-check \
  -H 'Content-Type: application/json' -H 'X-Api-Key: <your header-auth value>' \
```

## 6. Roadmap to "best in class"

Ordered by value per effort. Items 2, 3, 5 and 7 from the earlier version of this list are done in v4.1.

1. **Parallelise the full report** (M7). Move Keywords, Backlinks, PageSpeed, Content Review and AI Visibility into sub-workflows started with Execute Workflow (no wait) and merge on completion; the wall-clock drops from ~20 to ~7 minutes and each module becomes independently testable and reusable through the API.
2. **Monthly cost roll-up**: `run_ledger` is per run; a Data Table or sheet that sums it per customer/month lets you price with margin.
3. **Hosted report link**: publish the PDF behind a signed URL so emails carry a link rather than a 200 KB attachment.
4. **Durable rate limiting and job tracking** (M6): a Data Table keyed by execution id with status (accepted / running / done / failed), which also powers a `GET /status/:id` endpoint for API customers and a "check my report" page for form users.
5. **Prompt re-tune on Sonnet 5.5**: the agents now run on Sonnet 5.5; after the first live runs, compare a few briefs/drafts against v3 outputs and adjust wording if needed.
6. **Quality evals for the content path**: keep 10–20 real briefs/drafts, score them with a rubric (keyword placement, no invented facts, FAQ format, table present), and run the set whenever a prompt changes. Content QA already produces most of the signals.
7. **Apply the production overlay** (`production/PRODUCTION.md`) before customer traffic, and move report email to a transactional sender on your domain.
8. **Competitor and cluster quality** (M11, L3): SERP-overlap clustering and service-based seed queries make the discovery report noticeably sharper.
9. **Ladder follow-ups**: e-mail the user (not only ops) when a ladder page run is rejected by the budget or rate guard; let the tracker start the next rung automatically when `ladder_auto_next_rung` is on (today recommend-only); treat unknown difficulty (KD null) explicitly in the rung bands; let discovery's tiering promote a very high-opportunity cluster into "Now" even when it is informational; use RDAP before DataForSEO WHOIS in the full report ($0.48 of the $1.02 run).
10. **Tracking follow-ups** (see `TRACKING_FEATURE_SPEC.md`): Bing Webmaster Tools and Google Business Profile as further sources; charts in the PDF from the stored daily series and a hosted per-site dashboard reading `seo_site_metrics` / `seo_query_history`; feed Search Console striking-distance queries into discovery and ladder planning; auto-run the recommended improvement when `ladder_auto_next_rung` is on; prune `seo_query_history` after 12 months.
11. **E-E-A-T follow-ups (v4.4)**: one live content run per page role with a real profile; several authors per site (pick by topic) instead of one default author; an author page generator (bio, credentials, list of articles, Person schema) from the profile; Site Admin actions to delete a profile or a case study; a case-study prompt in the Monday report for sites with none; transcripts fetched automatically (YouTube Data API captions need OAuth — today the owner pastes them); local pages planned by the ladder for geo head terms.
12. **Monitor follow-ups (v4.5)**: AI-visibility trend charts from `seo_ai_visibility`; brand-name disambiguation (a short domain label like "techand" can match another company — set `brand_names` through Site Admin `monitors`); Google Business Profile through the official API (OAuth) for reviews and posts; a status page per prospect for outreach tracking; diff-aware fix pack (only what changed since the last audit); Bing / Copilot as an AI engine when DataForSEO offers it.
